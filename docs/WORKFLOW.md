# 전체 작업 흐름

[README로 돌아가기](../README.md)

## 한눈에 보기

```text
자연어 요청 → 요청 파싱 ┬ 네이버 검색 → @Browser 공개 검색·출처 수집
                       └ 마이리얼트립 상품 → @Browser 전체 상품 증명·업체 이미지 번들
          → 공통 프롬프트 기반 분석·생성 → 원고 검증
          → 내부 배정·실행 서명 확인 → 임시저장/발행 → 히스토리 완료
```

가장 짧은 정상 요청은 다음과 같습니다.

```text
"서울 맛집" 1번 프로필, 블로그탭
```

검색 영역·개수·방식을 생략했으므로 통합검색에서 원고 10개를 만들고 프로필 1에 임시저장합니다.

마이리얼트립 상품 URL이 들어오면 검색 키워드와 URL을 분리하고 네이버 원고 1개를 만드는 전용 분기로 전환합니다.

## 1. 환경 준비

각 PC에서 저장소와 Codex 플러그인을 설치하고, Plugins Directory에서 **Browser**를 설치한 뒤 Computer Use를 활성화합니다. GitHub 저장소에는 코드와 문서만 공유되며, 환경과 사용자 데이터는 로컬에만 남습니다.

```text
Mato Blog Codex 초기 설정해줘.
```

Codex가 필요한 내부 부트스트랩을 수행합니다. 모바일에서 사용할 경우 먼저 [모바일 Remote 사용 안내](MOBILE_REMOTE.md)에 따라 이 PC를 호스트로 연결합니다.

## 2. 프로필 준비

이 프로그램에서 사용할 Codex 전용 프로필을 번호별로 등록합니다. 마토헬퍼 프로필은 발견·복사·공유하지 않으며, 각 사용자의 이 프로그램 전용 저장소에 새로 만듭니다.

```text
프로필 1,2를 만들고 번호, 별칭, 블로그 URL과 함께 보여줘.
```

각 프로필은 번호, 계정 별칭과 블로그 URL로 구분합니다. 블로그 ID 또는 URL을 등록하면 `https://blog.naver.com/<ID>`와 `https://blog.naver.com/<ID>?Redirect=Write&`를 자동 생성합니다. 프로필 생성은 `~/.googleblog/mato-blog-codex/browser_profiles/naver_N` 폴더와 메타데이터만 준비하며 Chrome은 별도 요청으로 엽니다. 플러그인 업데이트나 프로필 정보 수정은 이 폴더를 지우지 않고, 사용자가 `RESET-N`으로 해당 번호를 명시적으로 초기화할 때만 그 번호의 브라우저 데이터를 교체합니다.

```text
프로필 1,2 Chrome 창을 각각 열어두고 닫지 마.
```

열린 전용 창에는 loopback 연결기가 붙고 이후 로그인 확인과 업로드가 같은 창에 재연결됩니다. 사용자가 각 창에서 직접 로그인한 뒤 `로그인과 글쓰기 URL을 확인해줘. 창은 유지해줘`라고 요청합니다. 업로드가 시작되면 임시저장·발행 결과 확인이 끝날 때까지 창을 닫거나 다른 페이지로 이동하지 않습니다. 비밀번호나 세션 값은 플러그인 설정에 저장하지 않습니다.

각 네이버 계정에는 이름이 `제목을입력해주세요1:`인 내 템플릿과 `본문2:` 텍스트 블록을 준비하는 것을 권장합니다. `본문1:`·`인트로1:` 원고를 사용할 때는 같은 이름의 블록도 템플릿에 둡니다. 템플릿은 계정별로 따로 준비하며, 템플릿이 전혀 없으면 기본 편집기 타이핑 폴백을 사용합니다.

자세한 내용은 [프로필 사용 안내](PROFILE_GUIDE.md)를 참고하십시오.

## 3. 검색과 수집

Codex는 사용자의 한국어 표현을 다음처럼 해석합니다.

| 사용자 표현 | 동작 |
| --- | --- |
| 블로그탭 | 네이버 블로그탭 조사 |
| 통합검색 | 통합검색에 실제 노출된 블로그 글만 조사 |
| 검색 영역 생략 | 통합검색에 실제 노출된 블로그 글만 조사 |
| 개수 생략 | 10개 생성 |
| `10개` | 10개 생성 |
| 방식 생략 또는 임시저장 | 임시저장 |
| 발행·바로발행·자동발행 | 같은 요청에서 검증 후 공개 발행 |

Codex는 먼저 실행 폴더와 검색 시작 이벤트를 만든 다음 호스트 PC의 `@Browser`로 공개 검색 결과를 확인합니다. 화면에 노출된 순서를 유지해 최대 5개까지만 수집하고, 중복 URL은 제거하며 네이버 블로그 글 주소는 표준 `PostView` 형태로 정규화합니다.

통합검색에서 블로그 글이 2개만 보이면 2개만 사용합니다. 부족한 수를 블로그탭 결과로 채우지 않습니다. 결과가 하나도 없거나 접근 제한이 감지되면 다음 단계로 진행하지 않고 원인을 기록합니다.

Browser 수집이 끝나면 플러그인에 포함된 `naver_url_download.py`를 호출합니다. 각 출처는 `sources/items/<순위>_<제목>/` 아래 원본 TXT, `image_1.jpg`부터 `image_N.jpg`, 그리고 원문 제목·`인트로1:`·`본문2:`·`ㅂㅂㅂ` 소제목·표 셀·이미지 위치를 보존한 `<제목>_원본_함축.txt`를 저장합니다. 표는 `표 N x M 시작`/`(행,열)`/`표 N x M 끝` 형식으로 바뀌며 본문의 이미지 태그도 실제 파일명과 일치시킵니다. 이 단계는 Mato Helper 설치본이나 소스 경로에 의존하지 않습니다. 출처 URL을 본문에 유지하며 해시·EXIF·촬영일·소유권 메타데이터는 위조하지 않습니다.

다운로드 후에는 남겨진 이미지마다 EXIF 방향을 적용하고 GPS·EXIF·XMP·ICC를 제거한 뒤 같은 이름으로 재인코딩합니다. 출처 폴더의 `image-processing.json`에는 파일명·크기·처리 전후 SHA-256과 메타데이터 존재 여부만 기록하고 원래 메타데이터 값은 기록하지 않습니다. 네이버와 관계없는 본인 소유 또는 사용 허가 이미지 폴더에도 동일한 정리 모듈을 독립적으로 실행할 수 있습니다.

내 글 URL의 이미지를 원고마다 사용하라는 요청이면, 원고 생성 뒤 선택한 내 글 이미지 폴더를 원본 데이터셋으로 사용합니다. 원본은 한 번 정리하고, 생성된 원고 N개 각각에는 독립된 `image_N.jpg` 세트를 만들고 각 세트도 한 번씩 정리합니다. 따라서 원고 3개는 원고용 이미지 정리 3회와 원고별 `image-processing.json` 3개를 생성합니다. 이미지 태그가 없는 원고에는 순서대로 태그를 추가하며, 이후 원고 검증을 다시 수행합니다.

## 3A. 마이리얼트립 상품 URL 분기

마이리얼트립 상품 URL과 네이버용 제목 키워드를 함께 주면 일반 네이버 검색 수집을 실행하지 않고 상품 전용 분기로 처리합니다. 이 분기는 네이버 원고 1개만 지원합니다. `CPA 링크 <URL> 프로필 1 작업` 또는 `CPA 원큐 <URL> 프로필 1 작업`은 같은 분기를 한 줄로 실행하는 축약 명령이며, 기본 동작은 프로필 1 임시저장입니다.

```text
CPA 링크 https://myrealt.rip/iZRp3d 프로필 1 작업
```

```text
https://myrealt.rip/iZRp3d
메인키워드: 베트남 나트랑 투어
서브키워드: 아이랑, 부모님이랑, 비용
후킹: 솔직후기
동행: 시부모님, 아이 둘
경험노트: 사용자가 실제로 제공한 경험 사실만 입력
프로필 1 임시저장
```

입력 URL은 키워드로 섞지 않고 `product_url`에 입력 그대로 보존합니다. 상품 분기의 기본값은 네이버 채널·원고 1개·링크카드 대기 2초입니다. 현재 상품의 판매자 갤러리 사진은 상시 사용 승인 범위이며 별도 권한 문구를 요구하지 않습니다. 이미지 최대값은 1~80장이고 URL·원본 바이트·픽셀 중복을 제거한 고유 업체 사진이 80장을 넘으면 중단합니다.

Codex는 인앱 `@Browser`에서 검증된 상품 페이지를 열고 상품소개·포함/불포함·이용안내·필수정보·취소규정·후기 영역이 모두 존재하는지 확인합니다. 코스 영역은 상품에 따라 없을 수 있습니다. 전용 분류기가 내보낸 `available_sections`를 기준으로 실제 존재하는 상품소개·필수정보·후기를 펼치고, 코스는 있을 때만 펼친 뒤 후기 전체 보기, 모든 갤러리 슬라이드, 페이지 끝까지 확인합니다. 상품 이미지 후보 수가 두 번 연속 같아질 때까지 확인한 다음 렌더링 HTML을 전용 분류기에 먼저 넣어 정확한 후보 ID와 0부터 시작하는 `document_image_index`를 받습니다. 분류기는 라이브 `document.images`에 포함되지 않는 `noscript`·`template` 내부 이미지를 인덱스에서 제외합니다. 같은 라이브 DOM의 해당 이미지를 다시 확인해 렌더링 완료 상태, 실제 섹션, 펼친 영역, 스크롤 위치, 갤러리 방문 수, 후보·로드 수를 증명 JSON으로 남깁니다. 단순 HTTP HTML이나 검색 결과만으로 이 단계를 대신하지 않습니다.

상품 번들은 같은 상품의 판매자 제공 `gallery` 이미지만 허용합니다. 실제 투어 사진이 아닌 `introduction`·`itinerary`의 쿠폰·이벤트·혜택·안내 그래픽도 거부합니다. 여행자 후기 사진, 추천·다른 상품, 프로필, 자리표시자와 UI 이미지는 호스트가 비슷해도 거부합니다. 허용된 이미지는 중복을 제거해 응답 원본 바이트를 `originals/`에 보존하고, 업로드용 메타데이터 제거 JPEG를 `prepared/image_N.jpg`로 만듭니다. 실제 원고에는 모든 허용 이미지를 한 번씩만 사용합니다.

Codex는 준비된 모든 JPEG를 직접 확인해 이미지마다 보이는 장면만 요약합니다. 상품 파서는 같은 상품 번호의 제목·평점·후기 수·가격·소요 시간·포함/불포함·이용 조건을 구조화하고, 코스는 해당 섹션이 있을 때만 근거로 제공합니다. 후기 문장은 원고에 보존하지 않고 반복 경향과 해시만 남깁니다. 이어서 `공통.txt`를 수정하지 않은 채 공통 프롬프트와 이번 실행 전용 상품 오버레이를 함께 적용합니다. 제목 후보 5개는 메인 단어 전체, 서브키워드 1~2개와 후킹을 반드시 포함하며 지역 불일치와 과거 실행 제목 중복 페널티를 검사해 하나를 확정합니다. 시각 요약과 제목 키워드가 가장 잘 맞는 갤러리 사진 1~2장을 첫 대표 이미지로 정하고, 나머지는 상품소개·코스 역할에 맞춰 배치하되 파일 태그는 `image_1.jpg`부터 연속되도록 안전하게 다시 매핑합니다.

동행 정보는 독자 페르소나를 정할 뿐 실제 방문의 증거가 아닙니다. 1인칭 방문·구매·선택·만족이나 가족 반응은 사용자가 `경험노트`에 사실로 제공한 범위에서만 쓸 수 있습니다. 후기의 경험을 사용자 경험으로 바꾸거나, 경험노트가 없는데 다녀온 사람처럼 쓰지 않습니다.

후처리기는 확정 제목, 근거가 검증된 상품 주장, 이미지 위치와 입력 URL을 원고에 결합합니다. `본문2:`의 첫 번째와 마지막 비어 있지 않은 줄에는 입력받은 URL이 정확히 한 번씩, 총 두 번 들어갑니다. 원고 저장 뒤 `prepared/` 이미지를 재인코딩하지 않고 원고 폴더에 연결하며, 원고 1개·URL 2개·이미지 순서·출처 manifest·해시·사용 권한을 모두 검증한 뒤에만 네이버 입력으로 넘깁니다. 업로더는 두 URL 줄 각각에서 네이버 링크카드를 만들고 정확히 2초 기다립니다.

## 4. Codex 분석과 원고 생성

`@Browser`가 확인한 공개 자료와 내부 실행 자료를 현재 Codex가 읽고 다음을 수행합니다.

원고 규칙은 Codex가 임의로 만들지 않습니다. 최초 실행 시 플러그인의 기본 `공통` 프롬프트를 `~/.googleblog/mato-blog-codex/prompts/공통.txt`에 만들고, 이후에는 이 로컬 관리 파일을 우선 사용합니다. 사용자가 파일을 수정하면 다음 생성부터 그대로 반영되며, 실행 기록에는 프롬프트 키와 SHA-256을 남깁니다. 오늘 날짜 컨텍스트는 원고를 만들 때마다 동적으로 붙습니다.

1. 통합검색에 보이는 블로그 글을 최대 5개까지 모아 검색 의도, 반복되는 질문, 핵심 개념과 구성 공통점을 머지합니다.
2. 가격·정책·운영시간처럼 바뀔 수 있는 정보는 가능한 경우 공식 출처로 확인합니다.
3. 요청한 버전마다 서로 다른 제목, 관점과 소제목 구성을 정합니다.
4. 등록 프로필의 공개된 본인 글을 분석할 수 있으면 최근 3~5개에서 일반적인 문체 특성을 참고합니다.
5. `posts/`에 요청 수만큼 `_함축.txt`를 저장합니다.

원고 기본 형식은 다음과 같습니다.

```text
제목을입력해주세요1: 제목

본문2:
도입 문단

ㅂㅂㅂ첫 번째 소제목
본문

ㅂㅂㅂ두 번째 소제목
본문
```

Markdown 제목 기호는 넣지 않습니다. 사용자가 이미지 포함 로컬 원고를 요청하면 `[image_1.jpg]`부터 순서대로 태그를 넣고, 각 원고 폴더에 같은 이름의 JPEG를 복사합니다. 검증기는 태그와 파일의 순서·개수를 1:1로 확인합니다. 다른 글의 문장을 복제하거나, 실제로 하지 않은 방문·구매·사용 경험을 만들어내지 않습니다. 로컬 공통 프롬프트와 이 진실성 규칙이 충돌하면 허위 경험을 만들지 않는 규칙이 우선합니다.

검색 글에서 내려받은 이미지는 출처 URL과 함께 로컬 확인용으로 유지합니다. 다른 사람의 이미지를 발행하려면 사용자가 소유권 또는 사용 허가를 확인해야 하며, 확인 전에는 로그인·임시저장·발행 단계로 넘기지 않습니다.

## 5. 검증

검증기는 다음 조건을 확인합니다.

- 요청한 개수의 `_함축.txt`가 존재하는가
- 제목과 `본문2:`가 있고 본문이 비어 있지 않은가
- `ㅂㅂㅂ` 소제목 구조가 올바른가
- 제목이 중복되지 않는가
- 여러 버전이 사실상 같은 원고로 반복되지 않는가
- 검증한 파일 경로와 SHA-256이 이후 바뀌지 않았는가

검증을 통과하지 못하면 업로드하지 않고 문제 목록을 Codex가 수정하도록 합니다. 검증 뒤 원고 내용이나 경로가 바뀌면 기존 통과 상태는 무효이며 다시 검증해야 합니다.

## 6. 프로필 배정과 업로드 확인

선택한 프로필은 사용자가 적은 순서대로 라운드로빈 배정합니다. 프로필 `1,2,3`에 원고 10개를 배정하면 다음과 같습니다.

| 원고 | 프로필 |
| --- | --- |
| 1, 4, 7, 10 | 1 |
| 2, 5, 8 | 2 |
| 3, 6, 9 | 3 |

Codex는 먼저 프로필 번호·별칭·블로그 URL·원고 제목·방식과 배정표를 보여줍니다. 이 단계에서는 네이버에 쓰지 않습니다.

임시저장 요청은 Playwright가 연결한 로컬 전용 Chrome `naver_N` 프로필로 실행합니다. 업로더는 열린 프로필에 재연결해 `내 템플릿`의 `제목을입력해주세요1:`을 선택하고, 제목은 Mato Helper 방식으로 입력하며 일반 본문과 표 셀은 20ms 고정 지연으로 실제 타이핑합니다. `본문1:`·`인트로1:`·`본문2:` 영역, `ㅂㅂㅂ`·`소제목` 인용구, `!!` 구분선, 1×1 이상 표, 로컬 이미지와 URL 링크카드를 원고 순서대로 Smart Editor 동작으로 처리합니다. URL 한 줄만 네이버 링크카드 생성을 위해 운영체제 클립보드로 붙여넣고, 원고 전체 붙여넣기나 DOM 직접 삽입은 하지 않습니다. 템플릿이 없으면 기본 편집기 자리로 폴백해 같은 타이핑 루프를 사용합니다.

`발행`, `바로발행`, `자동발행`처럼 공개 발행 의도가 명시되면 배정표와 실행 서명을 내부 검증하고 같은 요청에서 실제 발행까지 진행합니다. 사용자에게 실행 ID나 승인을 반복해서 요구하지 않습니다.

## 7. 실행과 중단 처리

프로필별로 유지형 Chrome 연결기를 시작하거나 이미 열린 창에 재연결해 순차적으로 사용합니다. 각 프로필의 임시저장·발행 확인이 끝나면 해당 Chrome 창을 닫지 않고 대기 상태로 남겨두며, 그런 뒤 다음 프로필 작업으로 넘어갑니다. 이미 성공한 원고는 `run.json`에 기록되고 재개 시 건너뜁니다. 사용자가 창을 닫아 대상 페이지가 사라지면 해당 원고는 실패로 기록되고, 플러그인은 다른 계정으로 임의 재배정하지 않습니다.

공개 자료 조사용 `@Browser` 프로필과 업로드용 로컬 전용 Chrome `naver_N` 프로필은 서로 다른 저장소입니다. 내장 Browser 로그인 상태를 네이버 업로드 로그인으로 사용하지 않습니다.

다음 상황에서는 자동 우회 없이 작업을 중단합니다.

- 로그인이 만료됨
- CAPTCHA 또는 접근 제한이 표시됨
- 네이버 편집기 구조를 확인할 수 없음
- 선택된 템플릿에서 원고에 필요한 본문 영역 자리를 찾을 수 없음
- 업로드 중 프로필 Chrome 창이 닫힘
- 대상 프로필과 등록 블로그 URL이 일치하지 않음
- 발행 버튼 또는 성공 상태를 확실히 확인할 수 없음

중단 원인과 마지막 완료 항목은 실행별 `HISTORY.md`와 `run.json`에 남습니다. 문제를 해결한 뒤 동일한 실행 폴더를 사용하면 완료되지 않은 항목부터 재개할 수 있습니다.

저장·발행 버튼을 눌렀지만 성공 여부를 확실히 확인하지 못하면 해당 항목을 `uncertain`으로 남기고 자동 재시도하지 않습니다. 사용자가 네이버에서 직접 확인한 뒤 Codex에 실제 성공인지, 저장되지 않았는지를 알려주면 정확한 실행 ID와 엔트리 키로 상태를 해소하고 안전하게 재개합니다. 공개 발행 성공을 수동 확인할 때는 직접 글 URL도 필요합니다.

## 실행 폴더

일반적인 실행 폴더는 다음과 같습니다.

```text
바탕화면/YYYY-MM-DD/YYYYMMDD_HHMMSS_<검색어>/
├─ run.json
├─ HISTORY.md
├─ sources/
│  └─ sources.json
├─ analysis/
│  └─ common-patterns.json
└─ posts/
   ├─ v01_<제목>/
   │  └─ <제목>_함축.txt
   └─ v02_<제목>/
      └─ <제목>_함축.txt
```

날짜는 한국 시간 기준이며 같은 날 여러 번 실행해도 실행 시각과 검색어로 폴더가 구분됩니다. 실제 구조는 플러그인 버전에 따라 항목이 추가될 수 있습니다. 실행 폴더는 Git 저장소 밖의 로컬 바탕화면에 있으므로 GitHub에 자동으로 포함되지 않습니다.
