# 전체 작업 흐름

[README로 돌아가기](../README.md)

## 한눈에 보기

```text
자연어 요청 → 프로필 확인 → @Browser 공개 검색 → Codex 분석·생성
          → 원고 검증 → 내부 배정·실행 서명 확인 → 임시저장/발행 → 히스토리 완료
```

가장 짧은 정상 요청은 다음과 같습니다.

```text
"서울 맛집" 1번 프로필, 블로그탭
```

검색 영역·개수·방식을 생략했으므로 통합검색에서 원고 10개를 만들고 프로필 1에 임시저장합니다.

## 1. 환경 준비

각 PC에서 저장소와 Codex 플러그인을 설치하고, Plugins Directory에서 **Browser**를 설치한 뒤 Computer Use를 활성화합니다. GitHub 저장소에는 코드와 문서만 공유되며, 환경과 사용자 데이터는 로컬에만 남습니다.

```text
Mato Blog Codex 초기 설정해줘.
```

Codex가 필요한 내부 부트스트랩을 수행합니다. 모바일에서 사용할 경우 먼저 [모바일 Remote 사용 안내](MOBILE_REMOTE.md)에 따라 이 PC를 호스트로 연결합니다.

## 2. 프로필 준비

기존 Mato Helper 프로필이 있다면 Codex에 발견과 목록 표시를 요청합니다.

```text
기존 네이버 프로필을 찾아서 번호, 별칭, 블로그 URL과 함께 보여줘.
```

각 프로필은 번호, 계정 별칭과 블로그 URL로 구분합니다. 블로그 ID 또는 URL을 등록하면 `https://blog.naver.com/<ID>`와 `https://blog.naver.com/<ID>?Redirect=Write&`를 자동 생성합니다. 프로필 생성은 폴더와 메타데이터만 준비하며 Chrome은 별도 요청으로 엽니다.

```text
프로필 1,2 Chrome 창을 각각 열어두고 닫지 마.
```

열린 전용 창에는 loopback 연결기가 붙고 이후 로그인 확인과 업로드가 같은 창에 재연결됩니다. 사용자가 각 창에서 직접 로그인한 뒤 `로그인과 글쓰기 URL을 확인해줘. 창은 유지해줘`라고 요청합니다. 업로드가 시작되면 임시저장·발행 결과 확인이 끝날 때까지 창을 닫거나 다른 페이지로 이동하지 않습니다. 비밀번호나 세션 값은 플러그인 설정에 저장하지 않습니다.

각 네이버 계정에는 이름이 `제목을입력해주세요1:`인 내 템플릿과 `본문2:` 텍스트 블록이 필요합니다. 템플릿은 계정별로 따로 준비합니다.

자세한 내용은 [프로필 사용 안내](PROFILE_GUIDE.md)를 참고하십시오.

## 3. 검색과 수집

Codex는 사용자의 한국어 표현을 다음처럼 해석합니다.

| 사용자 표현 | 동작 |
| --- | --- |
| 블로그탭 | 네이버 블로그탭 조사 |
| 통합검색 | 통합검색에 실제 노출된 블로그 글만 조사 |
| 검색 영역 생략 | 통합검색에 실제 노출된 블로그 글만 조사 |
| 개수 생략 | 10개 생성 |
| `10개` | 10개 생성 |
| 방식 생략 또는 임시저장 | 임시저장 |
| 발행·바로발행·자동발행 | 같은 요청에서 검증 후 공개 발행 |

Codex는 먼저 실행 폴더와 검색 시작 이벤트를 만든 다음 호스트 PC의 `@Browser`로 공개 검색 결과를 확인합니다. 화면에 노출된 순서를 유지해 최대 5개까지만 수집하고, 중복 URL은 제거하며 네이버 블로그 글 주소는 표준 `PostView` 형태로 정규화합니다.

통합검색에서 블로그 글이 2개만 보이면 2개만 사용합니다. 부족한 수를 블로그탭 결과로 채우지 않습니다. 결과가 하나도 없거나 접근 제한이 감지되면 다음 단계로 진행하지 않고 원인을 기록합니다.

Browser 수집이 끝나면 플러그인에 포함된 `naver_url_download.py`를 호출합니다. 각 출처는 `sources/items/<순위>_<제목>/` 아래 원본 TXT, `image_1.jpg`부터 `image_N.jpg`, 그리고 원문 제목·`인트로1:`·`본문2:`·`ㅂㅂㅂ` 소제목·표 셀·이미지 위치를 보존한 `<제목>_원본_함축.txt`를 저장합니다. 표는 `표 N x M 시작`/`(행,열)`/`표 N x M 끝` 형식으로 바뀌며 본문의 이미지 태그도 실제 파일명과 일치시킵니다. 이 단계는 Mato Helper 설치본이나 소스 경로에 의존하지 않습니다. 출처 URL을 본문에 유지하며 해시·EXIF·촬영일·소유권 메타데이터는 위조하지 않습니다.

다운로드 후에는 남겨진 이미지마다 EXIF 방향을 적용하고 GPS·EXIF·XMP·ICC를 제거한 뒤 같은 이름으로 재인코딩합니다. 출처 폴더의 `image-processing.json`에는 파일명·크기·처리 전후 SHA-256과 메타데이터 존재 여부만 기록하고 원래 메타데이터 값은 기록하지 않습니다. 네이버와 관계없는 본인 소유 또는 사용 허가 이미지 폴더에도 동일한 정리 모듈을 독립적으로 실행할 수 있습니다.

내 글 URL의 이미지를 원고마다 사용하라는 요청이면, 원고 생성 뒤 선택한 내 글 이미지 폴더를 원본 데이터셋으로 사용합니다. 원본은 한 번 정리하고, 생성된 원고 N개 각각에는 독립된 `image_N.jpg` 세트를 만들고 각 세트도 한 번씩 정리합니다. 따라서 원고 3개는 원고용 이미지 정리 3회와 원고별 `image-processing.json` 3개를 생성합니다. 이미지 태그가 없는 원고에는 순서대로 태그를 추가하며, 이후 원고 검증을 다시 수행합니다.

## 4. Codex 분석과 원고 생성

`@Browser`가 확인한 공개 자료와 내부 실행 자료를 현재 Codex가 읽고 다음을 수행합니다.

원고 규칙은 Codex가 임의로 만들지 않습니다. 최초 실행 시 플러그인의 기본 `공통` 프롬프트를 `~/.googleblog/mato-blog-codex/prompts/공통.txt`에 만들고, 이후에는 이 로컬 관리 파일을 우선 사용합니다. 사용자가 파일을 수정하면 다음 생성부터 그대로 반영되며, 실행 기록에는 프롬프트 키와 SHA-256을 남깁니다. 오늘 날짜 컨텍스트는 원고를 만들 때마다 동적으로 붙습니다.

1. 통합검색에 보이는 블로그 글을 최대 5개까지 모아 검색 의도, 반복되는 질문, 핵심 개념과 구성 공통점을 머지합니다.
2. 가격·정책·운영시간처럼 바뀔 수 있는 정보는 가능한 경우 공식 출처로 확인합니다.
3. 요청한 버전마다 서로 다른 제목, 관점과 소제목 구성을 정합니다.
4. 등록 프로필의 공개된 본인 글을 분석할 수 있으면 최근 3~5개에서 일반적인 문체 특성을 참고합니다.
5. `posts/`에 요청 수만큼 `_함축.txt`를 저장합니다.

원고 기본 형식은 다음과 같습니다.

```text
제목을입력해주세요1: 제목

본문2:
도입 문단

ㅂㅂㅂ첫 번째 소제목
본문

ㅂㅂㅂ두 번째 소제목
본문
```

Markdown 제목 기호는 넣지 않습니다. 사용자가 이미지 포함 로컬 원고를 요청하면 `[image_1.jpg]`부터 순서대로 태그를 넣고, 각 원고 폴더에 같은 이름의 JPEG를 복사합니다. 검증기는 태그와 파일의 순서·개수를 1:1로 확인합니다. 다른 글의 문장을 복제하거나, 실제로 하지 않은 방문·구매·사용 경험을 만들어내지 않습니다. 로컬 공통 프롬프트와 이 진실성 규칙이 충돌하면 허위 경험을 만들지 않는 규칙이 우선합니다.

검색 글에서 내려받은 이미지는 출처 URL과 함께 로컬 확인용으로 유지합니다. 다른 사람의 이미지를 발행하려면 사용자가 소유권 또는 사용 허가를 확인해야 하며, 확인 전에는 로그인·임시저장·발행 단계로 넘기지 않습니다.

## 5. 검증

검증기는 다음 조건을 확인합니다.

- 요청한 개수의 `_함축.txt`가 존재하는가
- 제목과 `본문2:`가 있고 본문이 비어 있지 않은가
- `ㅂㅂㅂ` 소제목 구조가 올바른가
- 제목이 중복되지 않는가
- 여러 버전이 사실상 같은 원고로 반복되지 않는가
- 검증한 파일 경로와 SHA-256이 이후 바뀌지 않았는가

검증을 통과하지 못하면 업로드하지 않고 문제 목록을 Codex가 수정하도록 합니다. 검증 뒤 원고 내용이나 경로가 바뀌면 기존 통과 상태는 무효이며 다시 검증해야 합니다.

## 6. 프로필 배정과 업로드 확인

선택한 프로필은 사용자가 적은 순서대로 라운드로빈 배정합니다. 프로필 `1,2,3`에 원고 10개를 배정하면 다음과 같습니다.

| 원고 | 프로필 |
| --- | --- |
| 1, 4, 7, 10 | 1 |
| 2, 5, 8 | 2 |
| 3, 6, 9 | 3 |

Codex는 먼저 프로필 번호·별칭·블로그 URL·원고 제목·방식과 배정표를 보여줍니다. 이 단계에서는 네이버에 쓰지 않습니다.

임시저장 요청은 Playwright가 연결한 로컬 전용 Chrome `naver_N` 프로필로 실행합니다. 업로더는 열린 프로필에 재연결해 `내 템플릿`의 `제목을입력해주세요1:`을 선택하고, 제목과 본문을 Mato Helper 지연값으로 실제 타이핑합니다. `본문2:` 자리, `ㅂㅂㅂ` 소제목, 표 마커와 `[image_N.jpg]`를 원고 순서대로 Smart Editor 동작으로 처리합니다. 템플릿을 찾지 못하면 전체 본문 붙여넣기로 바꾸지 않고 중단합니다.

`발행`, `바로발행`, `자동발행`처럼 공개 발행 의도가 명시되면 배정표와 실행 서명을 내부 검증하고 같은 요청에서 실제 발행까지 진행합니다. 사용자에게 실행 ID나 승인을 반복해서 요구하지 않습니다.

## 7. 실행과 중단 처리

프로필별로 열린 Chrome 연결기 또는 같은 영구 프로필 컨텍스트를 순차적으로 사용합니다. 이미 성공한 원고는 `run.json`에 기록되고 재개 시 건너뜁니다. 사용자가 창을 닫아 대상 페이지가 사라지면 해당 원고는 실패로 기록되고, 플러그인은 다른 계정으로 임의 재배정하지 않습니다.

공개 자료 조사용 `@Browser` 프로필과 업로드용 로컬 전용 Chrome `naver_N` 프로필은 서로 다른 저장소입니다. 내장 Browser 로그인 상태를 네이버 업로드 로그인으로 사용하지 않습니다.

다음 상황에서는 자동 우회 없이 작업을 중단합니다.

- 로그인이 만료됨
- CAPTCHA 또는 접근 제한이 표시됨
- 네이버 편집기 구조를 확인할 수 없음
- `제목을입력해주세요1:` 내 템플릿 또는 `본문2:` 자리를 찾을 수 없음
- 업로드 중 프로필 Chrome 창이 닫힘
- 대상 프로필과 등록 블로그 URL이 일치하지 않음
- 발행 버튼 또는 성공 상태를 확실히 확인할 수 없음

중단 원인과 마지막 완료 항목은 실행별 `HISTORY.md`와 `run.json`에 남습니다. 문제를 해결한 뒤 동일한 실행 폴더를 사용하면 완료되지 않은 항목부터 재개할 수 있습니다.

저장·발행 버튼을 눌렀지만 성공 여부를 확실히 확인하지 못하면 해당 항목을 `uncertain`으로 남기고 자동 재시도하지 않습니다. 사용자가 네이버에서 직접 확인한 뒤 Codex에 실제 성공인지, 저장되지 않았는지를 알려주면 정확한 실행 ID와 엔트리 키로 상태를 해소하고 안전하게 재개합니다. 공개 발행 성공을 수동 확인할 때는 직접 글 URL도 필요합니다.

## 실행 폴더

일반적인 실행 폴더는 다음과 같습니다.

```text
바탕화면/YYYY-MM-DD/YYYYMMDD_HHMMSS_<검색어>/
├─ run.json
├─ HISTORY.md
├─ sources/
│  └─ sources.json
├─ analysis/
│  └─ common-patterns.json
└─ posts/
   ├─ v01_<제목>/
   │  └─ <제목>_함축.txt
   └─ v02_<제목>/
      └─ <제목>_함축.txt
```

날짜는 한국 시간 기준이며 같은 날 여러 번 실행해도 실행 시각과 검색어로 폴더가 구분됩니다. 실제 구조는 플러그인 버전에 따라 항목이 추가될 수 있습니다. 실행 폴더는 Git 저장소 밖의 로컬 바탕화면에 있으므로 GitHub에 자동으로 포함되지 않습니다.

## 8. 히스토리 완료

각 단계는 한국 시간으로 시작·완료·실패 이벤트를 추가합니다. 실행별 기록과 PC 전체 기록은 기존 내용을 덮어쓰지 않고 이어 씁니다. 기록 내용은 [히스토리 기록 형식](HISTORY_FORMAT.md)을 참고하십시오.

Python 스크립트의 직접 실행은 일반 사용자 워크플로가 아닙니다. 개발·진단이 필요한 경우에만 [개발자·내부 문제 해결 명령](COMMANDS.md)을 사용합니다.
